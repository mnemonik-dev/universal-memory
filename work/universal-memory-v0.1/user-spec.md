# User Spec: Universal Memory v0.1 — довести до отгружаемого релиза

## Что делаем

Код универсальной памяти написан (задачи 1-14, плюс PR #1, который починил проводку
адаптеров к движку gbrain). Но **ничего из обещанного не доказано**: сборка и тесты
никем не проверяются автоматически, качество поиска ни разу не измерено, установить
проект одной командой нельзя, облачный режим ни разу не работал с настоящей базой,
а семантический (векторный) поиск — главная функция — вообще не выполняется в тестах.

v0.1 — это релиз доказательств, а не новой функциональности. Мы закрываем разрыв
между «написано» и «работает у пользователя».

Девять пунктов:

1. **CI (continuous integration, автоматическая проверка на каждый push и PR).**
   Сегодня файла `.github/workflows/` не существует вообще. PR #1 был влит с нулём
   проверок. Заводим пайплайн: инициализация подмодулей, установка, `bun run test`,
   end-to-end smoke-тест (`scripts/mcp-smoke.ts`), gitleaks (поиск утёкших секретов).
2. **Настоящая проверка типов.** `bun run typecheck` сейчас пустышка: `tsconfig.json`
   нет нигде в репозитории, поэтому `tsc --noEmit` печатает справку и выходит с кодом 1.
3. **Датасет RUMBA доступен.** `research/RUMBA` — это gitlink без записи в `.gitmodules`,
   папка пустая. Из-за этого `packages/eval/run.py` физически не может загрузить данные.
4. **Первый прогон RUMBA.** «Benchmark-driven quality» заявлено в README как принцип,
   но ни одной цифры не существует. Получаем RecallAccuracy@5 и AnswerQuality, кладём
   результат в репозиторий, ставим цифры в README.
5. **Семантический поиск покрыт тестами.** Все прогоны идут в режиме BM25-only (без
   ключа эмбеддингов), то есть ветка `hybridSearch` — векторный поиск + RRF (Reciprocal
   Rank Fusion, слияние рангов) — не выполняется ни в одном тесте.
6. **Облачный путь проверен настоящим Postgres.** `cloud.test.ts` проверяет только
   поведение при отсутствии `DATABASE_URL`; `cloud.unit.test.ts` работает на моке.
   Нужен интеграционный тест против реального Postgres + pgvector.
7. **Подпись Mnemonik проверена вживую.** В каждом прогоне логи говорят
   `MNEMONIC_JWT not set` / `MNEMONIC_IDENTITY not set`. Проверяемое происхождение —
   ключевое отличие продукта, и оно ни разу не выполнялось от начала до конца.
8. **Установка одной командой.** Сервер сам печатает пользователю
   `bunx universal-memory setup`, но пакет никуда не опубликован, а `gbrain` подключён
   как `workspace:`-зависимость поверх git-подмодуля, что `npm publish` не разрешит.
   Сегодня установка — это клон, инициализация подмодулей и два `bun install`.
9. **Релиз.** Один живой инстанс по `DEPLOY.md`, проверенный снаружи по HTTPS с
   Bearer-токеном, актуализированный README и тег `v0.1.0`.

## Зачем

Проект остановился 27 июля 2026 на задаче 14 и пролежал до сентября с незакрытым
PR #1, который блокировал даже сборку из чистого клона. Сейчас блокер снят, тесты
зелёные (362 из 362), smoke-тест проходит. Это ровно тот момент, когда проект либо
доводится до отгрузки, либо снова расходится с реальностью: без CI следующая
регрессия попадёт в main незамеченной, как это уже произошло с фиктивным API
движка, которое пережило 373 «зелёных» теста на моках.

## Что НЕ входит (переносится в v0.2)

- `memory_sync`: pull и bidirectional (сейчас возвращают 0 с предупреждением).
- Ингесторы разговоров, голоса и структурированных исследований из `architecture.md`
  (есть только web и файлы).
- Хранение `source` на уровне отдельной памяти (сейчас теряется при capture).
- Возврат на upstream-пин gbrain после вливания экспорта `./think`.

Обоснование: пункты 1-9 доказывают то, что уже заявлено пользователю; эти четыре —
новая функциональность, и они не блокируют первый релиз.

## Критерии приёмки

- **AC1.** Push в main и любой PR запускают CI; красный тест блокирует влитие.
- **AC2.** `bun run typecheck` реально компилирует проект и падает на ошибке типа.
- **AC3.** `packages/eval/run.py --dry-run` находит датасет и отрабатывает без ошибок.
- **AC4.** В репозитории лежит файл результатов RUMBA с датой, версией и цифрами;
  те же цифры стоят в README.
- **AC5.** Существует тест, который выполняет `hybridSearch` с настоящим провайдером
  эмбеддингов и проверяет, что семантический (не дословный) запрос находит документ.
- **AC6.** Существует тест `CloudAdapter` против настоящего Postgres + pgvector,
  проходящий полный цикл add → getById → search → delete → clear.
- **AC7.** Задокументирован и воспроизведён живой цикл подписи: sign → verify с
  настоящими `MNEMONIC_JWT` и `MNEMONIC_IDENTITY`.
- **AC8.** Установка описана и проверена как одна команда на чистой машине.
- **AC9.** Живой инстанс отвечает на MCP-вызов снаружи по HTTPS; README не содержит
  устаревших утверждений; поставлен тег `v0.1.0`.

## Риски

- **R1.** Задачи 5, 6 и 7 требуют внешних ресурсов (ключ эмбеддингов, Postgres,
  учётные данные Mnemonik). Если ключа нет — тест обязан пропускаться явно и громко,
  а не тихо превращаться в BM25-only, как сегодня.
- **R2.** Публикация в npm упирается в `gbrain` как подмодуль. Решение может
  потребовать публикации форка или бандлинга — это архитектурное решение, а не
  упаковочная мелочь; оно принимается в задаче 8 и записывается в `decisions.md`.
- **R3.** RUMBA может показать результат хуже базовой линии mem0. Это допустимый
  исход: цифра важнее, чем красивая цифра. Провал порога не блокирует релиз, но
  обязан быть записан в README честно.
