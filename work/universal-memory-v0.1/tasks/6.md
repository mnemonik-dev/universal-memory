# Task 6: Locked-down perimeter — proxy, custom CA, fail-closed egress

## Description

The requirement is that this works inside a secured enterprise environment. Two things
stand in the way. The ingestion fetcher knows nothing about proxies — the string
"proxy" does not appear anywhere in `src/` except a comment about nginx — so pulling a
URL from behind a corporate gateway fails. And the current failure mode for a missing
provider is silent degradation, which in a perimeter is exactly backwards: the system
must refuse rather than quietly reach outside.

## What to do

- Make the ingestion fetcher honour `HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY` and a
  custom certificate authority bundle, so `memory_capture` on a URL works from inside a
  perimeter that intercepts TLS. Keep the existing SSRF protection intact — proxy
  support must not become a way to reach `localhost` or link-local addresses.
- Add a fail-closed egress switch (`NO_EGRESS` or similar): when set, the server refuses
  to start if a third-party embedding or chat provider is configured, and refuses
  outbound fetches to anything but the configured internal hosts. It fails loudly at
  startup, not on the first request.
- Write down the data-flow posture as a short document: with the self-hosted provider,
  what leaves the perimeter is nothing — no document text, no queries, no embeddings.
  That statement is what makes the system approvable by a security reviewer, so it must
  be exact rather than reassuring.
- Confirm secret scrubbing holds on every path a corporate deployment would log:
  startup, authentication failure, provider error, ingestion error.
- State clearly which constraints were tested against a real corporate network and which
  were modelled (risk R3). Do not claim a perimeter we did not have.

## TDD Anchor

- `fetcher_uses_https_proxy_when_set` — with a proxy configured, the request goes
  through it.
- `fetcher_still_blocks_localhost_through_proxy` — SSRF protection survives the change.
- `no_egress_refuses_third_party_provider_at_startup` — configured with OpenAI and
  `NO_EGRESS`, the server exits with a message naming the conflict.
- `no_egress_blocks_outbound_fetch` — a capture of an external URL is refused, not
  attempted.

## Acceptance Criteria

- [ ] URL ingestion works through an HTTPS proxy with a custom certificate authority
- [ ] Existing SSRF blocking is intact and tested through the proxy path
- [ ] `NO_EGRESS` with a third-party provider configured fails at startup, loudly
- [ ] `NO_EGRESS` blocks outbound fetches rather than attempting them
- [ ] A data-flow posture document states exactly what leaves the perimeter
- [ ] No secret appears in startup, authentication, provider or ingestion error logs
- [ ] Tested-versus-modelled constraints are stated
