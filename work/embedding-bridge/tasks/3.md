# Task 3: Sidecar storage for relative vectors

## Description

Add the `um_relative_vectors` table, owned by `memory-hub`, working identically on
PGLite (local) and Postgres (cloud). `vendors/gbrain` is not touched (Decision D2).

## What to do

1. `packages/memory-hub/src/storage/migrations/001_relative_vectors.sql` — the DDL
   from the tech spec. Must be idempotent (`IF NOT EXISTS` throughout) and must run
   unchanged on PGLite and Postgres; if a type differs between them, pick the
   portable one (`BYTEA`, `TIMESTAMPTZ`).
2. `packages/memory-hub/src/storage/relative.ts`:
   - `ensureRelativeSchema(engine)` — run the migration, idempotent, called once at
     adapter init.
   - `upsertRelative(engine, {memoryId, userId, anchorSetId, embedModel, relVec})`
     — `ON CONFLICT (memory_id, anchor_set_id) DO UPDATE`.
   - `listRelative(engine, {userId, anchorSetId, excludeEmbedModel?})` — returns
     rows for bridged scan; `excludeEmbedModel` skips rows the native path covers.
   - `countByModel(engine, {userId, anchorSetId})` — for backfill progress and eval.
3. float32 ↔ `BYTEA` codec: little-endian, explicit, with a length check on read.
   Do not rely on the driver's array handling — PGLite and node-postgres differ.
4. Wire `ensureRelativeSchema` into `LocalAdapter` and `CloudAdapter` init.
   `HybridAdapter` delegates; it must not open its own connection.

## TDD anchors

- Migration runs twice with no error and no duplicate table.
- Round-trip of a 1024-float vector is bit-exact on PGLite and on Postgres.
- Upsert on the same `(memory_id, anchor_set_id)` replaces rather than duplicates.
- A row with a different `anchor_set_id` for the same memory coexists (Decision D6).
- `listRelative` with `excludeEmbedModel` omits exactly the matching rows.

## Done when

Contract tests pass against both engines. The Postgres test is skipped with an
explicit message when no `DATABASE_URL` is set — never silently passed.
