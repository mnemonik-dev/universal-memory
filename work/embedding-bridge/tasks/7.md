# Task 7: Attest the anchor set through Mnemonik

## Description

Make the shared basis provable rather than assumed. Two clients that both claim to
use `um-anchors-v1` should be able to verify it, not trust it.

## What to do

1. Define the anchor-set manifest: `{ schema: "UM_ANCHOR_SET_V1", version, n,
   anchor_set_id, sha256_of_corpus_file, created_at }`. The manifest carries the
   id and the file digest — **not** the 1024 anchor strings themselves; the corpus
   ships in the repo and is fetched by digest.
2. `adapters/mnemonik/` — `attestAnchorSet(manifest)`: canonical CBOR → blake3 →
   COSE_Sign1 via `@mnemonik-xyz/sdk`, stored as a normal attestation. Anchoring
   on Arweave/Solana is the operator's choice via the existing
   `mode: "local" | "participate"` field; local is the default.
3. `verifyAnchorSet(attestationId, localCorpusPath)` — fetch the attestation,
   verify the signature, recompute `anchor_set_id` and the file digest from the
   local corpus, and fail loudly on any mismatch.
4. Surface `anchor_set_id` and, when present, `anchor_set_attestation` on MCP
   recall results, so a consuming client can check which basis produced a hit.
5. **Never attest user relative vectors** (Decision D5). Only this manifest and
   existing memory hashes go anywhere near an anchor. Task 8 verifies this.

## TDD anchors

- Manifest → attestation → verify round-trip succeeds.
- A single edited byte in the corpus file fails `verifyAnchorSet`.
- Verification against a manifest for a different `anchor_set_id` fails.
- The attested payload contains no anchor strings and no user data (assert on the
  serialized bytes, not on intent).

## Done when

Round-trip and all three tamper tests are green in `local` mode. `participate`
mode is exercised only if a funded keypair is configured.
