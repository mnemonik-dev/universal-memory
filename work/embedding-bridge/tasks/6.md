# Task 6: Cross-embedder eval — THE GATE

## Description

Measure whether the bridge actually works on our three providers. Per Decision D3
this gates the merge: Tasks 7 and 8 do not start until this is green, and a
failure closes the feature.

## Prerequisites — satisfied 2026-09-06

The dataset is now reachable. It was not when this task was written: `research/RUMBA`
was a gitlink with no `.gitmodules` mapping, pinned to `ba08160`, which does not exist
on the remote — the identical dead-pin failure gbrain had (v0.1 decisions F1).

- Mapped to `https://github.com/ai-forever/RUMBA.git` and re-pinned to `a20471a`.
- `git submodule update --init research/RUMBA` now succeeds.
- `python3 packages/eval/run.py --dry-run` validates it: **85 dialogues, 1543 QA
  pairs** — matching the harness's own note about the full 1543-sample English set.
- Each QA entry carries `question`, `answer`, `evidence`, `category`, so Recall@k is
  computable directly from the dataset's own evidence spans.

## Metric validity — why this gate is sound without an LLM judge

The harness's AnswerQuality is a substring heuristic (`run.py` says so in its own
comment), while the stored mem0 baseline is an LLM-judge score. That mismatch makes
the *mem0 comparison* unusable — and this gate does not use it.

This gate is **self-relative**: every off-diagonal cell is scored against the diagonal
cell of the same `query_model`, on the same dataset, with the same metric. A
deterministic Recall@k over the dataset's evidence spans is comparable to itself, which
is all a ratio requires. No judge, no baseline, no cross-harness comparison.

Two constraints follow, and they are load-bearing:

- **Recall@k only.** AnswerQuality does not enter the gate, in either direction.
- **The mem0 baseline is not a gate and is not to be cited as one.** `run.py` now
  prints that caveat at every run.

## What to do

1. `packages/eval/src/cross-embedder.ts` — for each ordered pair
   `(write_model, query_model)` over {openai, google, ollama}:
   - ingest the RUMBA corpus (`research/RUMBA`) under `write_model`;
   - run the benchmark queries under `query_model`;
   - record Recall@1, Recall@5, Recall@10, MRR@10, and p50/p95 query latency.
2. Emit a 3×3 matrix per metric. The diagonal is the same-embedder baseline; every
   off-diagonal cell is reported both absolutely and as a fraction of the diagonal
   cell for its `query_model`.
3. Sweep N ∈ {256, 512, 1024, 2048} by truncating the 1024-anchor set
   (and extending to 2048 if needed — a different `anchor_set_id`, per D6). Report
   the full sweep, not just the winner.
4. Record brute-force scan latency at 10k / 100k / 1M relative rows (Decision D4).
5. Write results, including the negative ones, into `decisions.md` as a dated
   entry with the raw numbers inline.

## Gate

- **Pass:** every off-diagonal Recall@10 ≥ 85 % of its `query_model` diagonal, at
  some N ≤ 2048. Ship the smallest passing N, flip `UM_BRIDGE` default to `on`.
- **Re-open D1:** any cell in the 60–85 % band → evaluate a learned mapping
  (vec2vec, [arXiv:2505.12540](https://arxiv.org/abs/2505.12540)) before shipping.
- **Fail:** any cell < 60 % → close the branch. Record why in `decisions.md`.
  A silently-wrong cross-provider search is worse than an honest "not supported".

## Running it

```
git submodule update --init research/RUMBA        # dataset (a20471a)
python3 packages/eval/run.py --dry-run            # validates harness + dataset, measures nothing
python3 packages/eval/run.py --top-k 10 --service universal-memory --backend local
```

Requires Bun on PATH and all three embedding providers reachable — the matrix needs
{openai, google, ollama} keys or endpoints. A missing Bun is now a hard error rather
than a silent dry run (see the 2026-09-06 entry in `decisions.md`). Results are written
to `packages/eval/results/`, inside this repository, not into the submodule.

## Done when

The matrix is committed to `decisions.md` and one of the three gate outcomes is
explicitly declared there. "Looks promising" is not an outcome.
